# User-guide docs site — plan

Status: **in progress** — scaffold + screenshot harness shipped
(`docs-site/`, `npm run docs:shots`), and the schedule walkthrough content is
written (`docs-site/guide/schedule/`). Remaining: the deploy seams (Dockerfile,
pages.yml, gate/CI) and real content for the admin guide.

Goal: user-facing walkthroughs of the apps (starting with schedule + admin),
generated as a static site and deployed **alongside the app in both places** —
the GitHub Pages static site and the deployed container.

## Decisions

- **Vitepress**, not Jekyll. Jekyll was the original idea, but it adds a Ruby
  toolchain to an otherwise Node-only repo (CI, local preview, and especially
  the container build). Vitepress is markdown + Vue, uses the Node 26 already
  in CI and the Docker build stage, and emits plain static HTML/CSS/JS. MkDocs
  (Python, already present for the pipeline) was the other candidate.
- **`docs-site/` is the Vitepress root** — not `docs/`, which holds the repo's
  internal dev docs and is deliberately not deployed.
- **`base: '/docs/'`** so one build works at both
  `skiadas.github.io/catalog-vis/docs/` and
  `catalog.harisskiadas.com/docs/`.
- Screenshots are **generated by Playwright** from a committed, declarative
  manifest (see below), not hand-taken.

## Deploy seams (verified)

- **Container** — `server/src/index.js` serves everything under
  `express.static(config.staticDir)`, so dropping the built site at
  `/srv/static/docs` is served at `/docs/` with **no server code change**.
  `Dockerfile`: the build stage runs `npm run build:docs`; the runtime stage
  copies `/src/docs-site/.vitepress/dist` to `/srv/static/docs`.
- **GitHub Pages** — `pages.yml` already assembles `_site/` and writes
  `.nojekyll` (Jekyll stays off; docs are prebuilt files). Add
  `npm run build:docs` and copy `docs-site/.vitepress/dist` to `_site/docs/`.

## Tooling

| Thing | Where |
| --- | --- |
| `vitepress@^1.6.x` | root devDependency (installed by the existing `npm ci`) |
| `npm run dev:docs` | `vitepress dev docs-site` (local preview) |
| `npm run build:docs` | `vitepress build docs-site` |
| `npm run docs:shots` | regenerate screenshots from the manifest |
| `build:docs` in `scripts/gate.mjs` (+ `ci.yml`) | broken docs fail fast |
| `.gitignore` | `docs-site/.vitepress/dist`, `docs-site/.vitepress/cache` |

`npm run build` stays apps-only so the e2e webServer runs are not slowed.

## Screenshot harness — workflow as committed data

The important part: codify **which PNG represents which state of the app**, so
regeneration is one command and the mapping is reviewable.

`docs-site/screenshots/manifest.mjs` — one entry per screenshot:

```js
{
  file: 'schedule-access.png',        // stable name the docs reference
  app: 'schedule',                    // launcher | schedule | browse | planner
  as: 'registrar',                    // demo identity that signs in
  route: '/#/schedule/<id>/access',   // the access dialog is its own route now
  seed: 'populated-schedule',         // named DATA fixture (API-level)
  steps: [                            // declarative UI state (not in the URL)
    { act: 'settle' },
    { act: 'assert', role: 'dialog', name: 'Access' },
  ],
  fullPage: false,
  alt: 'The access dialog: who can see and suggest changes for a schedule',
}
```

- **Why steps exist**: many states are *not* URL-addressable today (dialogs,
  mode toggles, filters). The manifest records them explicitly. The route
  redesign has already turned the manage surface into a route (`/#/schedules`)
  and the access dialog into an overlay route (`/#/schedule/<id>/access`), and
  is expected to shrink the rest to the genuinely sequential/transient cases;
  walkthroughs stay step-based regardless.
- **DSL** (`capture.mjs`, a small executor): `goto`, `signin`, `click`
  (accessible role/name — the app is a11y-gated), `fill`, `select`, `key`,
  `settle`, `assert`, plus a rare `custom` escape hatch. Settle after every
  step, same discipline as the e2e suite.
- **`assert`** makes “this PNG = this state” a checked claim: the shot is only
  taken if the declared state is actually present.
- **Fixtures** (`fixtures.mjs`) are named, UI-independent data seeding routines
  (create schedules/terms/directory users via the API), reusable by future e2e.
- Output: `docs-site/public/screenshots/<file>` (Vitepress public dir),
  referenced from markdown as `/docs/screenshots/<file>`. Demo data only
  — fictional users; never real directory names or the live DB.
- Fresh scratch DB per run; fixed viewport/scale; username auth — same recipe
  as `playwright.config.js`.
- Committed PNGs, regenerated on demand. An optional `--check` (re-render and
  diff) is **off by default** — visual gates are flaky across Chromium
  versions.

## Docs-side binding (so references cannot drift)

- A small Vitepress component, e.g. `<Shot file="manage-access-dialog.png" />`,
  renders a `<figure>` with the manifest's `alt`/caption.
- Build-time validation in the Vitepress config: every `<Shot file=…>` must
  exist in the manifest, and every manifest entry must have a file on disk.
  A stale name fails the docs build instead of embedding a dead image.

## Content scope

- `docs-site/index.md` — landing.
- `docs-site/guide/schedule/` — the walkthroughs, aimed at non-technical
  readers (plain language, exact UI labels in bold): getting around; your
  schedules; sharing; the views; conflicts; where a course can hide;
  editing vs suggesting; adding a course; changing a course; adding a lab;
  submitting changes; downloading a CSV; a glossary.
- `docs-site/guide/admin.md` — directory + CSV import (still a skeleton).
